# CPPC 首选核、C-State 与 SMT：调度三兄弟与 Windows 协同

> **分类**：BIOS 与固件 · 核心调度与电源管理（第二季 EP04）
>
> **风险等级**：🟢 低（三项设置全部完全可逆，改错或缺失联动的典型症状为单核爆发力下降、待机功耗激增或多线程性能倒挂，不会损坏硬件芯片）。
>
> **一句话**：超频管的是性能上限，调度管的是性能给谁用。CPPC 首选核管“活分给谁”，C-State 管“闲到多深”，SMT 管“一核几线”；首选核生效必须依赖 BIOS 发令方与 Windows 官方驱动/电源计划执行方的“三件套完整联动”，“半套联动等于没联动”；默认三项全开即为最优解。

---

## 常见翻车症状与调度层定位

在完成了 PBO 开关、PPT/TDC/EDC 功耗电流墙以及频率偏移等“超频层”的调优后，处理器的理论加速能力已经就绪。然而，许多玩家在日常体验或基准测试中经常遇到以下让人困惑的翻车症状：

1. **单核加速频率看着很高，单线程跑分却跑不出来**：在任务管理器或监控软件中瞬态能看到 5.4GHz 甚至 5.7GHz，但单核跑分或单线程轻负载游戏帧率偏低，后台任务经常被丢到体质最差的核心上执行；
2. **待机功耗与风扇转速居高不下**：电脑开机后什么都没运行，CPU 核心电压却始终死死卡在 1.3V 以上，待机功耗达到几十瓦，风扇呼呼转，无法回落到十几瓦以内的静音休眠状态；
3. **照抄网传攻略关掉 SMT，游戏不仅没涨帧，生产力直接腰斩**：跟着“关超线程提高游戏单核帧率”的民间偏方关闭 SMT，游戏帧率没有本质变化甚至微卡顿加剧，渲染压片、代码编译或解压缩性能直接暴跌 20%~30%；
4. **后续玩 Curve Optimizer (CO) 负压降压频频低负载蓝屏**：高负载拷机几小时稳如泰山，但只要待机挂机、打开浏览器或者看视频时就突然黑屏重启或报错 WHEA-Logger Event 18。

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   超频层 vs 调度层：处理器执行控制模型                  │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│   【超频层】  PBO / 功耗墙 (PPT/TDC/EDC) / Boost Override ──► 性能上限 │
│   （管的是芯片在安全温度与电气约束下“最高能冲多高频率”）               │
│                               ▲                                        │
│                               │ （能力就绪，等待任务派发）             │
│                               ▼                                        │
│   【调度层】  CPPC / C-State / SMT ───────────────────────► 性能给谁用 │
│   （管的是操作系统与硬件如何把计算任务分配给最合适的物理/逻辑单元）    │
│                                                                        │
│   ┌───────────────────┬───────────────────┬────────────────────┐       │
│   │ CPPC / 首选核心   │ Global C-State    │ SMT (同步多线程)   │       │
│   ├───────────────────┼───────────────────┼────────────────────┤       │
│   │ 活分给谁？        │ 闲到多深？        │ 一核几线？         │       │
│   │ 优先派发最佳体质核 │ 闲置下电与电压回落 │ 逻辑线程与吞吐权衡 │       │
│   └───────────────────┴───────────────────┴────────────────────┘       │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

**核心铁律**：**超频管上限，调度管分配**。调度层不对，上限再高也白搭。若调度机制缺失，任务被机械式摊平，不仅好核闲置、差核跑重载，待机功耗与低负载稳定性也会全盘失控。

## 适用范围与硬件边界

- **架构平台**：AMD 桌面平台 **AM4** 与 **AM5**（从 Zen 2 / 锐龙 3000 系列起全面引入 CPPC2 规范，并在 Zen 3 / 5000 系列、Zen 4 / 7000 系列及 Zen 5 / 9000 系列中持续深度协同）；
- **X3D 处理器特殊边界**：
  - **单 CCD X3D 处理器（如 5800X3D / 7800X3D / 9800X3D）**：所有物理核心均可均等访问片上 3D V-Cache，调度机制相对单纯，**坚决保持“三全开”**（CPPC 开、C-State 开、SMT 开）即可；
  - **双 CCD X3D 处理器（如 7900X3D / 7950X3D）**：属于不对称异构设计（CCD0 带 3D V-Cache，CCD1 为高主频无 3D 缓存核心）。此类芯片不仅依赖 BIOS CPPC，还必须依赖 Windows 11 下的 AMD 3D V-Cache 性能优化驱动、AMD PPM Provisioning 驱动与 Xbox Game Bar 协同实现“核心停靠（Core Parking）”，在运行游戏时将任务精准钉在 Cache CCD 上；
- **移动端笔记本**：笔记本平台（锐龙 H/HS/HX 系列）受限于 OEM 电池续航与散热标定，C-State 与 CPPC 通常在出厂即强制固化开启，BIOS 界面若提供相关开关切勿轻易关闭。

## 旋钮一：CPPC 与 CPPC Preferred Cores（活分给谁）

### 1. 物理本质与体质排序表

在 BIOS 的 AMD CBS 或 CPU Configuration 页面中，通常能看到两个关联选项：

- **CPPC**：Collaborative Processor Performance Control（协同处理器性能控制，基于 ACPI 6.2+ 标准）；
- **CPPC Preferred Cores**：首选核心（或称为最高体质核心优先调度）。

在过去传统的调频机制（如旧版 ACPI P-States）下，操作系统按粗粒度的阶梯档位请求频率，CPU 各核心被视作完全同质的单元。

然而在现代芯片制造工艺中，即使在同一块芯片硅片（Die）上，各个核心的硅晶体质也存在微小差异。AMD 从工厂封装测试时，就会将每个物理核心的最高电气耐受频率与电压敏感度进行精确测量，生成一张**核心体质排序表**并固化在硬件熔丝（Fuse）中。

- **CPPC 的作用**：将调频决策权从操作系统软件层下放给 CPU 硬件自主微秒级调节（响应速度比传统软件机制快数千倍）；
- **CPPC Preferred Cores 的作用**：由 CPU 硬件将体质最好（能以最低电压冲上最高频率）的核心（通常标记为“金核”或“银核”）标识暴露给 Windows 操作系统调度器。

```text
┌────────────────────────────────────────────────────────────────────────┐
│                     CPPC 首选核心调度决策链路                          │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│   【硬件层 / 发令方】                                                  │
│   CPU 芯片出厂熔丝 ──► 核心体质表：Core 0 (标称98) / Core 1 (标称100 金核)│
│                               │                                        │
│   BIOS 开启 CPPC + 首选核心 ──┘ 通过 ACPI CPPCv2 接口上报给 Windows    │
│                                                                        │
│   ────────────────────────── 跨越内核边界 ──────────────────────────  │
│                                                                        │
│   【操作系统 / 执行方】                                                │
│   Windows 11 内核调度器 ◄── AMD 官方芯片组驱动 (Provisioning Package)   │
│            │                                                           │
│            ▼ 依据 AMD Ryzen Balanced 锐龙平衡电源计划策略              │
│   单线程重载/前台主线程 ──► 精准投送给【Core 1 金核】跑满 5.4GHz 峰值   │
│   后台次要任务          ──► 分流给其余标准核心，杜绝争抢              │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

### 2. “三件套”联动机制与“半套联动”陷阱

**首选核要真正生效，必须三件套完整闭环：**

1. **BIOS 发令方**：开启 `CPPC` 与 `CPPC Preferred Cores`（部分主板为 `Enabled` 或 `Auto`）；
2. **驱动通信层**：安装较新版本的 **AMD 官方芯片组驱动**（Chipset Drivers 3.10.08.506 或更新版本，提供 AMD Processor Provisioning Package）；
3. **系统执行方**：在系统电源管理中处于协同工作状态（Windows 10 下激活 **AMD Ryzen Balanced** 锐龙平衡电源计划；Windows 11 下由 Windows 自带平衡计划加载 AMD 芯片组特调配置文件协同管理）。

> ⚠️ **深度避坑：半套联动等于没联动**
>
> 许多用户以为在 BIOS 里打开了 CPPC 开关就大功告成，这属于典型误区：
> - **BIOS 是发令方，Windows 才是真正派发任务的执行方**。BIOS 只负责上报排序表，如果操作系统端缺少 AMD 官方芯片组驱动，或者被某些“系统优化工具”强行删除了电源调度配置，Windows 调度器根本读不懂这些标记；
> - 最终表现就是：调度机制退化为机械式的盲目轮询分摊，单核爆发任务经常落在体质一般的核心上降速执行，金核反而闲置，导致单核性能与游戏最低帧劣化（详见 AMD 官方知识库 PA-400 规范）。

### 3. 三个反例与典型误区

- **反例 A：使用 Ghost / 第三方“极限精简版”系统**：精简版系统往往精简了 Windows 电源预配包与驱动签名，导致 AMD 芯片组驱动无法正确下发调度策略；
- **反例 B：无脑开启“卓越性能 / 高性能”电源计划**：部分玩家迷信所谓的“卓越性能模式”。在某些配置下，该模式会将核心最低执行状态硬锁为 100%，破坏了 CPPC 的动态频阶感知；
- **反例 C：手动全核固定倍频超频未关首选核**：若玩家在 BIOS 中锁死全核 4.8GHz @ 1.25V，由于所有核心频率已被硬件锁死，首选核心已无意义。此时建议关闭首选核心，避免调度器浪费资源做无谓的线程迁移。

## 旋钮二：Global C-State Control（闲到多深）

### 1. 物理本质与待机功耗闸门

- **英文全称**：Global C-State Control（全局 C 状态控制）；
- **物理定义**：**处理器空闲下电休眠闸门**。

根据 ACPI 规范，CPU 在不同负载下工作于不同的 C 状态：
- **C0**：Operating State（核心满载或执行指令中，核心供电完全激活）；
- **C1 / C1E**：Halt State（停机状态，停止指令执行，时钟门控断开）；
- **C6 / Deep Sleep**：深度休眠状态（核心内部寄存器与缓存状态转存，核心内部供电被硬件晶体管完全切断，漏电流降至接近零，核心电压回落至近 0V）。

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   Global C-State 的能耗与电压行为                      │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│   【C-State 开启 (默认/健康)】                                         │
│   轻载/待机 ──► 核心逐级坠入 C6 深度休眠                               │
│   核心电压   ──► 从 1.35V 瞬时大幅降至 0.2V~0.6V 乃至彻底断电          │
│   整机功耗   ──► 待机功耗回落至十几瓦，整机冰凉且风扇停转              │
│                                                                        │
│   【C-State 盲目关闭 (民间误区)】                                      │
│   轻载/待机 ──► 核心被强制截流在 C0/C1 浅层停机                        │
│   核心电压   ──► 始终死死顶在 1.30V~1.40V 高电位                       │
│   整机功耗   ──► 待机持续四五十瓦，积热严重，加速芯片硅退化            │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘
```

**为什么默认必须开？**
开启 C-State 是现代 CPU 实现能效比奇迹的基石。在核心无需工作时下电断电，不仅能极大地削减日常待机功耗与噪音，更能将宝贵的功耗墙（PPT）和温度空间完整留给正在重载运行的工作核心。

### 2. 进阶伏笔：为什么 C-State 是 Curve Optimizer (CO) 的必查前置

许多进阶玩家热衷于通过 Curve Optimizer 进行“全核负压降压”。然而在实操中，最让人头疼的故障往往不是“拷机死机”，而是**“闲置蓝屏（Idle Crash / Low-load Crash）”**：

- **故障机理**：重载拷机时，频率高、电压高，负压偏移尚在安全区间；但当用户放下鼠标离开电脑、或者打开一个简单网页时，核心迅速切入低负载低频率状态。
- **瞬态崩盘**：若此时 C-State 是开启的，核心电压会在毫秒级别内大幅下坠。如果玩家的 CO 负压给得太激进，叠加 C-State 下探的低电压后，核心供电瞬间低于该硅片维持逻辑电路运作的最低临界阈值，直接引发 **WHEA-Logger Event 18（APIC ID 处理器故障）**，电脑瞬间黑屏重启。
- **调优纪律**：**切勿通过“关闭 C-State”来掩盖 CO 降压不稳的假象**！关掉 C-State 确实会让待机电压硬挺着不降，从而看似“解决了待机蓝屏”，但这是以常态高压高热、牺牲芯片寿命与待机功耗为代价的饮鸩止渴。正确的做法是：**保持 C-State 开启，微调收敛失稳核心的 CO 负压数值**。

## 旋钮三：SMT（一核几线）

### 1. 物理本质：单核双线程

- **英文全称**：Simultaneous Multithreading（同步多线程，AMD 对应 Intel Hyper-Threading 超线程技术）；
- **物理定义**：**通过复制一份架构寄存器状态，让单个物理核心在硬件层伪装为两个逻辑处理器**。

CPU 内部拥有许多运算单元（整数 ALU、浮点 FPU、加载存储等）。在执行单线程代码时，受限于指令并行度与内存读写等待，运算单元经常出现短暂闲置。SMT 允许第二条线程穿插利用这部分零碎算力，从而提高核心整体吞吐量。

### 2. 36 款游戏实测辨析：关 SMT 游戏飞升是真的吗？

在游戏社区中，“关超线程/关 SMT 能大幅提升游戏帧率”的言论长盛不衰。其理论依据是：关闭 SMT 后，每个核心只跑一个线程，独占所有 L1/L2 缓存与内部队列，消除两条线程在核心内部争抢算力资源带来的微延迟。

**综合权衡**：
为了极少数特定老游戏中那点甚至无法肉眼察觉的极微弱帧率波动，去换取整机生产力与后台多任务能力暴跌三成，属于典型的**高代价、低收益**行为。因此，除非进行专业极限跑分或做严格受限的单一游戏单兵对照测试，否则**绝不推荐在日常使用中关闭 SMT**。

## 实操验证与回滚三步法

### 1. 第一步：验证首选核心与驱动是否真正生效

1. 打开 **HWiNFO64**，展开 CPU 传感器列表：
   - 查看核心列表，确认是否有核心被标注为最高体质（如 `Core # Perf 1/1` 等标记）；
   - 在轻负载单核跑分（如 CPU-Z 单核测试或轻度任务）时，观察标记为首选核心的 `Core Effective Clocks`（有效时钟）是否率先冲到顶峰，而其余核心保持低频甚至休眠；
2. 检查驱动与电源配置：
   - 访问 AMD 官网，根据主板芯片组（B650/X670/B550 等）下载安装最新版 **AMD Chipset Drivers**；
   - 在设备管理器中检查 `System devices` 下是否存在 `AMD Provisioning Package Support Device`，确保驱动安装完整。

### 2. 第二步：验证 C-State 深度休眠与电压回落

1. 保持系统完全空闲（关闭所有前台大型应用，静置 1~2 分钟）；
2. 在 **HWiNFO64** 传感器视图中观察：
   - **`Core (Tdie/Tctl)` 核心温度**：待机温度应迅速回落至 40℃~50℃ 左右（受环境室温与散热规格影响）；
   - **`Core VID` / `Core VDDCR_CPU`**：空闲核心的电压应出现大幅回落；
   - **`Core C6 Residency`（核心 C6 驻留率）**：待机状态下各核心应有很高比例的时间处于 C6 休眠状态。

### 3. 第三步：误改或失稳回滚方案

若此前因照抄偏方关闭了某些选项导致异常，按以下步骤三步还原：

1. **进入 BIOS 恢复出厂设置**：
   - 开机按 `Del` 进 BIOS，在 `Advanced` 或 `AMD CBS / AMD PBS` 菜单中将 `CPPC`、`CPPC Preferred Cores`、`Global C-State Control`、`SMT Control` 全部重置为 **`Auto`** 或 **`Enabled`**；
2. **重置电源计划**：
   - 打开终端运行 `powercfg -restoredefaultschemes` 恢复系统标准电源配置，防止第三方工具修改的电源脚本残留；
3. **重新校准 CO 负压**：
   - 若开启 C-State 后发生待机蓝屏重启（WHEA 18），说明此前的 Curve Optimizer 负压过大。切勿去关 C-State，应将 CO 负压步进回调（例如从 `-25` 回调至 `-15`），直到通过长时间低负载挂机与重载拷机的双重稳定性测试。

## 📋 事实核查记录

| 待核查声明 / 规则 | 证据等级 | 核查结论 | 事实支撑与边界 |
| :--- | :---: | :---: | :--- |
| **关掉 SMT 能够大幅提升所有电脑游戏帧率** | ❌ 勘误 | 完全错误 | 36 款主流游戏实测表明开/关 SMT 互有胜负，总体平均帧无明显差异；但在视频压片、Cinebench 渲染等生产力多线程场景下关闭 SMT 会导致性能暴跌 20%~30%，得不偿失。 |
| **只要 BIOS 里开启了 CPPC，首选核就必定生效** | ❌ 勘误 | 不准确 | BIOS 只是发令方，负责向上提供核心体质数据；若 Windows 缺少 AMD 官方芯片组驱动或相关电源预配包，调度器无法感知，表现为任务机械摊平的“半套联动等于没联动”。 |
| **关闭 C-State 是彻底解决 Curve Optimizer 待机蓝屏的终极技巧** | ❌ 勘误 | 治标不治本 | 关闭 C-State 是用持续高电压、高功耗和高发热掩盖了低负载供电不足的瑕疵；正确做法是在保持 C-State 开启的前提下将激进的 CO 负压适当回调，保证瞬态电压安全。 |
| **现代锐龙日常使用必须保持 CPPC/C-State/SMT 三全开** | ✅ 属实 | 经过验证 | “三全开”是 AMD 架构师与系统调度器长期深度适配的标准设计规范，兼顾了单核峰值加速、低负载低耗节能与多线程极限吞吐。 |
| **双 CCD X3D 处理器（如 7950X3D）依赖核心停靠专属调度** | ✅ 属实 | 经过验证 | 双 CCD 异构芯片在游戏中需将任务锁定在 3D V-Cache CCD，依赖 AMD 官方驱动与 Xbox Game Bar 核心停靠机制协同，属于更高阶的异构调度范畴。 |
